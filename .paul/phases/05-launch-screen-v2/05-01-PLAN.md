<objective>
## Goal

Replace the flat launch banner with a designed launch screen: a large layered
SHERMAN wordmark, a single bordered two-column info panel carrying only true
content, and one welcome line — matching the *layout and craft* of the reference
screenshot in Sherman's own palette.

## Purpose

Phase 4 made Sherman own the screen. It does not yet own the *first impression*.
The current opener is a flat red wordmark and a three-circle mark with no
information on it: nothing about what Sherman can reach, how much it knows, or
how to drive it. The reference screenshot's value is not its colours — it is that
the first frame answers "what is this and what does it know" before you type.

This plan buys that, under one governing rule Evan set: **only true content.
Nothing invented.** The panel is worth having precisely because every number on it
is real — which today means it will honestly read near-zero, and that is the
point (R8: the brain is empty and should look it).

- One new non-UI module: vault stats reader
- Launch item swapped into the existing `<Static>` transcript
- 2 new smoke checks (80 cols and 200 cols, no overflow)

<facts_probed_at_plan_time>
Probed on ink 7.1.1 / react 19.2.8 / node v22.23.1, 2026-07-26. Recorded so APPLY
does not re-derive them and does not discover them the hard way.

1. **`renderToString(node, {columns})` exists and honours `columns`** (default 80),
   and it *does* capture `<Static>` output. This is the smoke-check mechanism —
   the launch screen can be rendered headlessly at any width with no TTY.

2. **A `<Box width={N}>` does not stretch on a wider terminal.** A width-76 box
   measured 76 at both 80 and 200 columns. **But a hardcoded 76 overflows at 60
   columns** (measured: maxVisualWidth 76 > 60). The panel width MUST be
   `Math.min(columns - 2, 76)`, never a constant. This is the single most likely
   way to ship "wrapped garbage".

3. **Wordmark geometry, measured:**
   - large form, 7-wide glyphs + 1 gutter → **55 visual columns × 7 rows**
   - small form, 5-wide glyphs + 1 gutter → **41 visual columns × 5 rows**
     (identical to the existing `logo/banner.ans` wordmark)
   Both verified by rendering. 55 fits inside 80 with 25 columns to spare.

4. **Visual width = strip `\x1b\[[0-9;]*m`, then count code points.** The block
   glyphs (`█ ▄ ▀`) are 3 bytes in UTF-8 but 1 column wide, so byte length lies.
   Any width assertion must count code points.

5. **The shell has ZERO slash commands.** Verified by grep across `shell/src/ui/`.
   The only real affordances are: Enter to send, Ctrl+C to interrupt/exit, and the
   CLI flags (`--raw`, `--probe`, `--version`, `--help`). See AC-3 — this changes
   what the "Commands" section can honestly say.

6. **Vault contents today:** `wiki/README.md`, `memory/shared/README.md`,
   `memory/private/evan-motovich/` (empty), `inbox/README.md`. Every `.md` present
   is scaffolding, not knowledge.

7. **`session.info` already carries `engine`, `model`, `user`, `vaultPath`,
   `threadId`.** `threadId` is null until the engine reports one — so at launch it
   is *always* null. Nothing new is needed from the engine layer, and this plan
   touches no file under `shell/src/engine/` (R12).
</facts_probed_at_plan_time>

<decisions_for_review>
Three judgment calls this plan makes. Each is cheap to reverse — flagged so Evan
can overrule at review rather than discover after APPLY.

### DR-1 — README.md files do NOT count toward vault totals

The vault holds four READMEs and no knowledge. Counting them renders
"1 wiki page · 1 shared fact" on a launch screen whose entire justification is
that its numbers are true. STATE.md is unambiguous that the brain is empty.

**Decision:** exclude `README.md` from every count. The panel will read `0` across
the board until real knowledge lands, which is honest and creates the right
pressure toward R8.

*Overrule by:* counting all `.md`, if you would rather the panel show file counts
than knowledge counts.

### DR-2 — the section is "Keys", not "Commands"; the footer says what is true

The brief asks for a "Commands" section and a `"/help for commands" equivalent`.
There are no commands (fact 5). Rendering a Commands section would either be empty
or invent entries — both fail the governing rule.

**Decision:** the section is titled **Keys** and lists the real affordances
(`enter` send · `ctrl+c` interrupt, again to exit). The footer's "equivalent" is
`ctrl+c to exit`. The moment a real command lands, the section is renamed and
repopulated — that is a one-line change.

*Overrule by:* naming it "Commands" and listing the CLI flags instead.

### DR-3 — engine · model lives in the footer only, not also in the left column

The brief puts `model · engine` in the left column *and* `engine + model` in the
footer of the same box. Printed twice inside one border it reads as a rendering
bug rather than a design.

**Decision:** left column = **identity** (user, vault path, session), footer =
**runtime** (engine · model · keys). Everything asked for is on screen, once.

*Overrule by:* accepting the duplication as specified.
</decisions_for_review>
