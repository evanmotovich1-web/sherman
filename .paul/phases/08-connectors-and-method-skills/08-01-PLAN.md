<objective>
## Goal

Replace the single hardcoded LLM-Wiki MCP block in `bin/sherman` with a
**declarative connector layer**: a repo-side catalog of known connectors, a
machine-side enablement-and-secrets file outside the repo, one renderer that
emits config for both engines, and a `/connectors` command that reports what is
actually wired versus what is blocked on a key.

## Purpose

Sherman can reach exactly one MCP server today, and only because a fifty-line
`if` block in the launcher knows its name. Every additional connector under that
design is another hardcoded branch, which means `0-1` (plan 08-02) would have no
surface to add a connector *to*. This plan builds that surface.

It also closes a standing gap: there is no smoke coverage of the MCP wiring at
all. The one part of Sherman that hands a live subprocess to the engine is the
part nothing tests.

## Output

- `agent/connectors.json` — the catalog (what exists, what it needs, where to sign up)
- `~/.sherman/connectors.json` — enablement + secrets, chmod 600, never committed
- `shell/src/connectors.js` — pure resolver: catalog + enablement → rendered set + blocked set
- `/connectors` shell command and its `capabilities.json` entry
- `bin/sherman` renders both engine configs from the resolver's output
- smoke check 24
- `docs/CONNECTORS.md`
</objective>

```gherkin

      recipe, its required secret names, and a signup URL

       connector-specific branch anywhere in the launcher
```

## AC-2: A connector missing its secret is reported, never half-wired

```gherkin
Given a connector is enabled in ~/.sherman/connectors.json but one of its
      required secrets is absent or empty
When   the launcher renders engine config
Then   the connector is omitted from both engine configs entirely, and the
       launcher prints one line naming the connector and the missing secret
```

## AC-3: Secrets never enter the repo, the vault, or a log

```gherkin
Given ~/.sherman/connectors.json holds an API key
When   the launcher renders config, /connectors prints, or smoke runs

       any printed output — only the secret's NAME and whether it is present
```

```gherkin
      connector known but not enabled
```

<task type="auto">
  <name>Task 1: The catalog, the resolver, and the secret boundary</name>
  <files>agent/connectors.json, shell/src/connectors.js, docs/CONNECTORS.md</files>
  <action>
    Write `agent/connectors.json` — the repo-side catalog of connectors Sherman
    KNOWS ABOUT. Same honesty law as capabilities.json: an entry describes a
    connector that really exists and really launches this way. Shape per entry:

      name        stable id, used as the MCP server name in both engines
      summary     one lowercase phrase, what it gives Sherman
      transport   "stdio" | "http"
      command/args (stdio) or url/headers (http), with ${VAR} placeholders
      requires    array of secret NAMES this connector cannot run without
      probe       optional: a command that must exit 0 for the connector to be
                  considered installed (this is how llmwiki's existing gate
                  generalizes)
      signup      { url, what } — where a human gets the credential and what to
                  ask for. This is what 0-1 reads when it must hand the operator
                  a checklist instead of wiring it silently.

    Seed it with llmwiki (transport stdio, probe = the venv CLI answering) so the
    catalog has a real, working, already-shipping entry from day one. Add no
    speculative entries: a connector that is not proven to launch does not belong
    in the catalog, for the same reason a capability that does not work does not
    belong on the launch screen.

    Write `shell/src/connectors.js` — a PURE resolver, no I/O side effects beyond
    reading the two files:

      loadCatalog(root)      -> {ok, connectors} | {ok:false, reason}
      loadEnablement(home)   -> {ok, enabled}    | {ok:false, reason}
      resolve(catalog, enablement, env) -> {
        wired:   [{name, transport, launch}]     ready to render
        blocked: [{name, missing:[secretName]}]  enabled but incomplete
        known:   [{name, summary, signup}]       catalogued, not enabled
      }

    Follow registry.js's discriminated-result convention exactly — `{ok:false,
    reason}` and never a plausible empty list, because "no connectors" and
    "unreadable connectors file" are different problems that must not look the
    same on screen.

    THE SECRET BOUNDARY, and it is the point of this task: `resolve` returns
    launch recipes with secrets ALREADY SUBSTITUTED for the renderer's use, and
    every other exported function returns names only. Anything that formats for
    display takes the `blocked`/`known` shapes, which carry no values. Add a
    `redact()` used on any error path that might otherwise echo a recipe.

    Write `docs/CONNECTORS.md`: what the two files are, why enablement lives in
    ~/.sherman and never the repo, how to add a connector by hand, and the rule
    that ~/.sherman/connectors.json is chmod 600 and never committed, synced, or
    written to the vault.
  </action>
  <verify>node -e "import('./shell/src/connectors.js').then(m=>console.log(Object.keys(m)))" lists loadCatalog, loadEnablement, resolve, redact; a resolve() call with a missing secret returns it under blocked and NOT under wired</verify>
  <done>AC-1, AC-3 satisfied: the catalog is data, and no export outside the renderer path can return a secret value</done>
</task>

<task type="auto">
  <name>Task 2: The launcher renders both engines from the resolver</name>
  <files>bin/sherman</files>
  <action>
    Replace the hardcoded llmwiki block (`bin/sherman` ~line 795-860) with a
    render step driven by `shell/src/connectors.js`.

    Because the launcher is bash 3.2 (C4) and the resolver is JS, the launcher
    shells out once: `node shell/src/connectors.js --render "$WORKSPACE"` writes
    `$WORKSPACE/.mcp.json` and prints the codex TOML block plus any blocked-
    connector NOTE lines on stderr. One node start per launch, same cost the
    existing wiki probe already pays.

    Rules the render step must hold, each one already established elsewhere in
    this repo:

    - `$WORKSPACE/.mcp.json` is REMOVED first and rewritten from scratch, so a
      connector removed from the catalog cannot survive a launch (the same
      reasoning as the skills `rm -rf` immediately above it).
    - The codex config gets `[mcp_servers.<name>]` appended once per connector,
      backed up first, and claimed only after read-back — the existing
      write_codex_model contract, unchanged.
    - A connector whose `probe` does not exit 0 is treated exactly as llmwiki's
      broken-venv case is today: omitted, with a NOTE naming the repair.
    - A blocked connector prints one line: name, the missing secret, and the
      signup URL from the catalog. Never the value.
    - If node is missing or the resolver throws, the launcher prints one NOTE
      and continues with NO mcp config rather than a partial one. Half-written
      engine config is worse than none — it fails at engine startup, far from
      the cause.

    Keep the LLM Wiki's behavior bit-for-bit: same probe, same repair NOTE, same
    resulting entries. It stops being a special case in code; it must not stop
    being a working connector.
  </action>
  <verify>Launch with the wiki installed → $WORKSPACE/.mcp.json contains llmwiki and codex config gains one [mcp_servers.llmwiki]; move the wiki aside → .mcp.json has no llmwiki and the repair NOTE prints; enable a fixture connector with no key → NOTE names the secret, and neither config mentions it</verify>
  <done>AC-2, AC-5 satisfied: both engines render from the catalog, and the wiki's shipped behavior is preserved</done>

## SCOPE LIMITS

- **No new connectors in the catalog beyond llmwiki.** Seeding it with services
  nobody has verified would put speculative entries in the one file whose value
  is that its entries are real. `0-1` adds entries; this plan builds the shelf.
- No UI work on the launch screen. Connector counts on the first frame are a
  separate question and this plan does not answer it.
- No secret encryption at rest. chmod 600 in `~/.sherman` is the same posture
  the engines' own credential files already use on this machine; anything
  stronger is a real key-management project, not a config change.
- No network calls in the launcher. Probes are local `--help`-shaped commands.
