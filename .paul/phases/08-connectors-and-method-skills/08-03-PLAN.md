<objective>
## Goal

Bring two planning methods into Sherman as company skills:

- **`evan`** — the PAUL loop (plan → apply → unify) and its full workflow,
  template, and reference set, renamed and vendored so it runs with no
  `~/.claude` on the machine.
- **`wayfinder`** — charting a body of work too big for one session as a map of
  decision tickets, adapted to Sherman's actual surfaces.

## Purpose

Both methods live today in Evan's personal `~/.claude` as Claude-Code slash
commands. That makes them unavailable to Codex, unavailable to anyone else in
the company, and dependent on absolute paths into a directory Sherman does not
ship. Ported, they become part of the product — which is what `skills/README.md`
means when it says the skills are the product.

The rename from `paul` to `evan` is Evan's call and is followed throughout.

## Output

- `skills/evan/` — SKILL.md router plus vendored `workflows/`, `templates/`,
  `references/`
- `skills/wayfinder/SKILL.md`
- Both registered in `skills/README.md`, both passing check 17
- smoke check 26
</objective>

  <action>
    Copy `~/.claude/paul-framework/{workflows,templates,references}` into
    `skills/evan/`, then rewrite. The `rules/` directory governs authoring the
    framework itself rather than using it — leave it behind; a skill ships the
    method, not the method's own style guide.

    Copy the 29 files in `~/.claude/commands/paul/` in as
    `skills/evan/references/commands.md` — ONE file listing each command, its
    purpose, and the workflow file it routes to. Twenty-nine near-identical
    front-matter stubs whose only job was to be Claude-Code slash commands are
    exactly the ceremony that does not survive the port; what survives is the
    routing table.

    Then, across every vendored file:

    - `paul` → `evan`, `PAUL` → `EVAN`, `/paul:x` → `/evan x`, preserving case.
    - `~/.claude/paul-framework/<x>` → the skill-relative path (`workflows/<x>`,
      `templates/<x>`, `references/<x>`). AC-2 is the point: after this rewrite,
      grep for `~/.claude` and for `/Users/moto` across `skills/evan/` must
      return nothing.
    - `.paul/` → `.evan/` for the project state directory, EXCEPT that the
      skill must state the legacy rule from AC-3: a project already holding a
      `.paul/` directory keeps it, and the skill reads and writes that one. This
      repo is such a project — `.paul/` here holds eight phases of real record —
      and a skill that renamed it on first use would orphan every cross-reference
      in it.
    - `@`-reference syntax: Claude Code expands `@file`; Codex does not. Rewrite
      the execution-context blocks to say "read <relative path>" in prose, so the
      instruction works on both engines. This is the same reasoning that keeps
      engine-specific detail out of skills entirely (AGENTS.md, R5).
    - `paul.toml` / `paul.json` manifest names → `evan.toml` / `evan.json`, with
      the same legacy-name rule as the state directory.

    Write `skills/evan/SKILL.md` as the router. Front matter: `name: evan`,
    `category: method`, a lowercase summary, and a description saying when to
    reach for it — multi-phase work that needs a plan of record, a loop that
    closes, and a written trail across sessions. Body:

    - The loop in three sentences: PLAN writes an executable plan, APPLY
      executes it, UNIFY reconciles plan against actual and closes it. The value
      is the written trail, not the ceremony.
    - The routing table: what the operator asks for → which workflow file to
      read. Keep it short; the workflows carry their own detail.
    - Where state lives (`.evan/`, legacy `.paul/`) and what each file is for.
    - **The autonomy reconciliation, and it needs saying explicitly.** The PAUL
      workflows are full of "wait for user response" and "confirm routing"
      gates, written for an interactive Claude Code session. Sherman's autonomy
      contract (`skills/README.md`, `agent/SYSTEM.md`) says those are decision
      material to resolve by default, not questionnaires to hand over. State
      that the vendored gates are read that way here — resolve them from the
      request and the evidence, and stop only under the contract's existing
      rule. Without this paragraph the ported method would quietly reintroduce
      the interview behavior the whole product removed.
    - One line pointing at `graph-engineering` for the shape of any plan whose
      tasks are independent, and at `wayfinder` for work too big to plan in one
      pass.
  </action>
