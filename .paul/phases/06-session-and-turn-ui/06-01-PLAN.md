<objective>
## Goal

Give every Sherman session a durable identity and give the first frame the
Hermes posture Evan asked for: a session id that appears on the launch screen,
in the adapter's memory-attribution rule, and on a JSONL session log; a version
header embedded in the panel border; a `sherman update` subcommand; and the
launch screen reorganized to the reference structure — retro SHERMAN AGENT
wordmark on top, identity block beneath it (model · company, folder, session),
filling the terminal viewport on entry.

## Purpose

Two forces meet here. Operationally: memory writes are about to matter (R8),
and a fact file nobody can trace to a user, a session, and a date is a fact
nobody can audit — attribution must exist *before* the vault fills, not after.
Experientially: Evan compared the opener against Hermes mid-conversation and
named the gaps — the first frame should own the whole screen, carry the model,
company, folder and session identity, and read as retro-deliberate rather than
compact-informational.

## Output

- Session id `YYYYMMDD_HHMMSS_<6 hex>` minted by `bin/sherman`, exported to
  both handoffs, spliced into the adapter, shown on the launch screen
- `~/.sherman/sessions/<id>.jsonl` — plain-append turn log (operational data,
  never the vault)
- Memory-attribution instruction in the assembled adapter
- `sherman update` subcommand with honest no-remote behavior
- Launch screen v3: SHERMAN AGENT two-deck wordmark, identity block, version
  header in the panel border, full-height first frame
- smoke: existing adapter check extended; ONE new check (`sherman update`)
</objective>

<facts_probed_at_plan_time>
Probed on ink 7.1.1 / react 19.2.8 / node v22.23.1 / macOS bash 3.2.57,
2026-07-26. Recorded so APPLY does not re-derive them.

1. **Text-in-border works and aligns.** Ink 7 supports per-side border control:
   a hand-drawn `<Text>` top line (`╭─ label ─…─╮`) over a `<Box borderStyle="round"
   borderTop={false}>` of the same width renders as ONE seamless bordered box with
   text embedded in its top edge. Verified at width 30: side borders line up
   exactly. This is the mechanism for the version header (and for 06-02's
   Sherman box label). The top line must be composed to the exact panel width —
   count code points, not bytes.

2. **Session-id recipe verified on system bash 3.2:**
   `"$(date +%Y%m%d_%H%M%S)_$(od -An -N3 -tx1 /dev/urandom | tr -d ' \n')"`
   matches `^[0-9]{8}_[0-9]{6}_[0-9a-f]{6}$`. No bash-4isms.

3. **`assemble_adapter(engine, user, vault)` in `bin/sherman` builds the body
   heredoc and awk-splices it into the wrapper template.** The attribution
   instruction belongs in that heredoc (after the private-memory block, before
   the hard-rule restatement) — NOT in the adapter templates, which stay
   engine-framing only. The launcher tail is: `assemble_adapter` → `cd
   $WORKSPACE` → `exec` (raw engine or shell). The id must be minted before
   assembly and exported before BOTH execs.

4. **`renderToString` defaults to 24 rows and `useWindowSize()` is blind to it**
   (STATE, 05-01). Full-height layout must therefore take an injectable `rows`
   prop exactly as `columns` does (D17 extended), or it cannot be tested off a
   TTY.

5. **Wordmark glyph math:** small table glyphs are 5 wide; AGENT is 5 letters →
   5×5 + 4 gutters = **29 columns**, comfortably under the 55-column SHERMAN
   deck. New glyphs needed: **G and T** (both tables); A, E, N exist.

6. **Colour strings must be `ansi256(N)`** — a bare index is silently dropped
   by Ink (root cause of the all-white v2 screen, fixed in `15fed16`; guarded
   by smoke check 9). Any new colour goes through `theme.c()`.
</facts_probed_at_plan_time>

## AC-1: One session id, everywhere it was promised
```gherkin
Given `sherman` launches the shell
When the launch screen renders and the adapter is assembled
Then the launch panel's session field shows an id matching
     ^[0-9]{8}_[0-9]{6}_[0-9a-f]{6}$ (dimmed, where "session: new" sat)
And the assembled workspace adapter contains the SAME id
And `sherman --raw` sessions get the same treatment (id minted + spliced)
And running `node shell/bin/sherman-shell.js` directly (no env id) mints its
    own id in the same format instead of crashing or showing blank
```

## AC-2: Session log is plain-append JSONL under ~/.sherman
```gherkin
Given a shell session with id S sends one prompt and receives one reply
When the turn completes
Then ~/.sherman/sessions/S.jsonl contains one line per turn side, each a JSON
     object with exactly {role, at, text} — role "user" then "sherman",
     at an ISO-8601 timestamp
And nothing under the vault path was written by the logger
And if the sessions directory cannot be created or appended, the shell
    continues working with no crash and no error spam
```

## AC-3: Memory attribution instruction reaches the adapter
```gherkin
Given the adapter is assembled for user U in session S on date D
When the assembled CLAUDE.md / AGENTS.md is read
Then it instructs that every fact file written to shared or private memory
     ends with the line "— U · S · D"
And the instruction lives in the assembled body (bin/sherman heredoc),
    not in adapters/*/ templates
```

## AC-4: Version header embedded in the panel border, honest under absence
```gherkin
Given the repo has git and a HEAD commit
When the launch panel renders
Then its top border reads ╭─ Sherman Abrams v<version> · <short sha>[ · +N] ─…╮
     with version read from shell/package.json and sha + dirty count from
     guarded git calls against the repo root
And with uncommitted files present the "+N" segment appears; with a clean tree
    it does not
And if git is missing or the root is not a repo, the sha and +N segments are
    OMITTED cleanly — border intact, no error, no empty "·" separators
And no "upstream" segment exists anywhere
```

## AC-5: `sherman update` behaves honestly in all three repo states
```gherkin
Given the repo has no git remote (today's state)
When `sherman update` runs
Then it prints the current version and "no update source configured" and exits 0

Given a repo with a remote (future)
When `sherman update` runs
Then it does git pull --ff-only, runs npm install in shell/ ONLY if the pull
     changed shell/package.json, runs ./smoke.sh, prints old -> new version;
     a non-ff or conflict prints "manual update needed" and exits nonzero;
     it never auto-merges

Given no git repo at all (future employee install)
When `sherman update` runs
Then it says updates come from the installer and exits 0
```
